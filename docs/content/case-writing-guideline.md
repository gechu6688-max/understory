# Understory 案例写作规范

本规范定义 Understory 标准案例的写作结构与编辑要求。Amazon case 是第一篇标准案例，也是后续案例的结构参照。规范约束写作方式，不改变现有内容架构、双语言实现或页面视觉。

## 标准结构

案例按以下顺序组织：

1. Case title
2. Introduction
3. Central Question
4. Quick Thesis
5. Entities / Topics / Concepts
6. Research Question / 核心问题
7. Background / 背景
8. Evidence / 关键证据
9. Analysis / 分析
10. Alternative Explanations / 其他可能解释
11. Limitations / 判断边界
12. Conclusion / 结论
13. What Would Change My Mind? / 什么证据会改变我的判断？
14. One More Question
15. References / 参考资料

页面顶部由 front matter 提供标题、引言、核心问题、简要判断与 taxonomy。正文负责展开论证。不要在正文中省略 Research Question，也不要用页面顶部的 Central Question 代替正文中的问题说明。

## 如何提出 Research Question

Research Question 应当是一个可以用证据讨论、存在合理争议、并且能形成有边界判断的问题。

- 从具体商业变化或决策出发，不从抽象口号出发。
- 问题应允许至少两种合理解释，不能预设结论。
- 明确分析对象、变化条件与可能结果。
- 避免把多个独立问题合并成一句话。
- 优先使用“在什么条件下”“发生变化后是否”“什么机制导致”等能够引导分析的表达。

Central Question 是页面顶部的简洁版本；正文 Research Question 可以进一步说明这个问题为什么重要、哪里存在张力，以及本文不会回答什么。

## 如何选择 Evidence

证据的作用是约束判断，而不是装饰观点。每一项关键证据都应能够支持、削弱或限定一个具体判断。

- 优先使用公司文件、监管资料、学术研究、官方数据和可核验的一手材料。
- 新闻报道主要用于事件背景、时间线或引用可追溯事实，不应独自承担核心因果判断。
- 区分事实、研究发现、监管指控、作者推断和仍未确认的信息。
- 说明比较基准、时间范围、样本边界和重要限制。
- 不因为数字醒目就使用数字；只有当它改变读者对问题的理解时，才放入 EvidenceHighlight。
- EvidenceHighlight 只呈现最关键的事实或比较，不替代正文解释，也不写成演示文稿式结论。

## Analysis 的要求

Analysis 必须解释证据与结论之间的机制，而不只是重复证据。

- 说明“为什么这项证据与问题有关”。
- 区分相关性、因果关系和条件性推断。
- 把公司行为、竞争环境、消费者结果和时间维度连接起来。
- 明确哪些结论能够从证据推出，哪些仍然只是合理推测。
- 使用商业概念解释机制，但避免堆叠术语。
- 每篇案例的 Topics 保持在 2–3 个，Concepts 保持在 2–3 个；只保留正文真正使用的概念。

## 如何保持中立判断

中立不等于没有判断，而是让判断受到证据和反方解释约束。

- 用同等认真程度呈现最强的 Alternative Explanations。
- 对监管指控、诉讼主张和公司说法标明其证据身份。
- 不把企业规模、成功或争议本身当作有害行为的证明。
- 不把低价、便利或效率自动视为无害，也不自动视为掩饰。
- 在 Limitations 中写清证据不能证明什么，以及结论不能推广到哪里。
- 在 What Would Change My Mind? 中列出能够削弱或加强当前判断的具体证据。

## Conclusion 写作原则

Conclusion 应给出明确但有边界的回答，并让读者理解这个回答成立的条件。

- 直接回应 Research Question，不引入新的核心证据。
- 先给判断，再说明判断的适用范围和条件。
- 避免“永远”“必然”“完全证明”等超出证据范围的表达。
- 不重复全文摘要；强调最重要的机制、权衡或条件。
- 结论之后保留开放性，让 One More Question 自然延伸到下一层问题。

## References 格式

每个来源使用结构化 metadata，并与正文中的关键主张保持可追溯关系。

必填字段：

- `id`：稳定、唯一、可读的来源标识。
- `title`：来源正式标题。
- `publisher`：发布机构、作者或媒体名称。
- `sourceType`：使用现有 schema 中的来源类型。
- `relevanceNote`：说明该来源支持什么，以及它不能证明什么。

按实际情况补充：

- `url`：尽量链接到原始来源或权威存档。
- `publicationDate`：来源发布日期。
- `accessDate`：网页或动态资料的访问日期。
- `relevanceNoteZh`：中文页面使用的自然中文说明，不做机械直译。

引用规则：

- 一条来源只承担它能够支持的主张。
- 诉状、监管新闻稿与判决必须明确区分。
- 公司文件可以说明业务、风险与公司立场，但不能单独证明外部影响。
- 学术研究应说明研究对象、比较方式与适用边界。
- References 保持完整来源结构；正文不重复堆放完整书目信息。

## 双语言编辑

- 英文与中文保持相同论证结构和证据边界。
- 中文优先使用自然的商业分析表达，不逐句机械翻译。
- 标准章节映射保持一致：Research Question → 核心问题；Evidence → 关键证据；Alternative Explanations → 其他可能解释；Limitations → 判断边界；What Would Change My Mind? → 什么证据会改变我的判断？
- 中文段落应控制长度，避免多个复杂判断连续挤在同一段中。
- 翻译可以调整语序和段落节奏，但不能改变论点、证据强度或不确定性程度。
